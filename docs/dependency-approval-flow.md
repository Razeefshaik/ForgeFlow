# Dependency approval at contribution start

The Engineer Handbook contribution to `ServerlessOpsIO/backstage-aws-sam-python-template` was screened as eligible after reading only its root README, then paused before coding because MkDocs/TechDocs packages were absent and downloads were disabled. Its environment planner correctly distinguished documentation checks from generated AWS deployment requirements. The application always passed `false` to initial execution's network argument, and the initial approval screen offered no download choice.

## Implementation plan and boundaries

1. Show explicit, default-off runtime/dependency download permission before requesting the approval preview. Bind that choice to the preview token, persisted immutable approval and contribution record. Forward it to initial execution rather than forcing offline. Changing permission or replaying a token with different permission must require a fresh preview.
2. Inspect nested dependency/build and documentation configuration, including MkDocs and Pipfile, without treating generated deployment workflows as repository contribution requirements. Save provisionable requirements separately from unsupported findings. Show them in approval so ordinary package installation is an expected setup step.
3. Tell the environment planner that an absent package pin is not a conflicting version requirement. With download approval, select compatible explicit versions and record the resolved dependency set in the environment recipe; preserve repository manifests and constraints. Offline mode must remain offline and pause only when the required artifacts cannot be provisioned from cache.
4. Verify permission propagation and token enforcement, nested documentation detection, no blanket AWS/template exclusion, and an actual disposable MkDocs/TechDocs build in the existing isolated container. Existing paused contributions require explicit recovery; no auto-resume, source change, AWS deployment or PR action is authorized by this application fix.

Use existing API/domain services, container provisioning and web controls. No new service or runtime dependency is needed for the application. Preserve audit history and the current contribution workspace.

## Verified results

The actual checkout's read-only screening now reads ten files, including `skeleton/crud/mkdocs.yml`, nested Python manifests and the relevant Makefile. It is eligible with provisionable dependency requirements and no unsupported findings. Generated AWS deployment workflows are not treated as mandatory handbook checks. The assessment export is a fixture replay of the actual local files, not a new GitHub assessment written into live application data.

`TestRealTechDocsEnvironment` downloaded **MkDocs 1.6.1** and **mkdocs-techdocs-core 1.7.1** in the existing isolated image provisioning path. The plugin's [official package metadata](https://pypi.org/project/mkdocs-techdocs-core/1.7.1/) supports Python >=3.9 and MkDocs >=1.6; Python 3.11 in the configured bootstrap satisfies this documentation requirement. These versions are validation fixture choices, not application-wide language/dependency defaults. The resolved transitive versions are recorded with `pip freeze --all` in preparation output.

The first real run passed in **231.96 seconds**, including installation, a strict offline build of a disposable copy of the actual CRUD handbook, offline image reuse and an offline rebuild containing a fixture-only documentation edit. The final run reused the matching image and passed in **34.95 seconds**, additionally proving cancellation removes a real container and its delayed child. Filesystem inspection confirmed both temporary repositories were removed. No verification containers remained. The prepared public dependency image is retained for reuse; no existing images, volumes or containers were pruned.

Eleven browser tests passed, including default-off approval, permission changes invalidating both preview and confirmation, propagation to proceed, and an explicit network-enabled recovery request from an environment pause. Real Git preparation tests prove the immutable permission reaches the execution callback and persists across idempotent requests. Changed permission cannot reuse an old token, and unapproved requests create no contribution.

Workspace, prerequisites, storage, discovery, API and execution suites passed during validation. An expanded execution run caught an overly broad unchanged-recipe exception; it was narrowed to an offline **blocked** environment receiving new approval. The four relevant environment/retry regressions then passed, including refusal to repeat an unchanged verification repair. Frontend production build, server build and `go vet ./...` passed. Static screening retains its existing file/request/time budgets, and the profile is now `prerequisites-v3`, forcing reassessment of older snapshots.

Evidence is preserved in `.cache/techdocs-approval-proof/`: `actual-handbook-prerequisites.json`, the original `techdocs-environment.jsonl`, `final/techdocs-environment.jsonl`, `techdocs-final.log` and `recovery-guards.log`. The owned demo proof server was stopped; the user's live server remained healthy on port 8080. The handbook contribution remains paused and requires explicit recovery after restarting ForgeFlow to load this backend change. In its Issue reactor, select **Allow downloading public dependencies when recovering this environment**, then **Allow downloads and recover**. This proof establishes dependency provisioning and handbook builds; it does not claim that issue #10 is implemented, independently reviewed or ready for a PR. No PR was submitted or merged.
